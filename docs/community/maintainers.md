# Maintainers

## Status — v0.1.0

**This is a pre-formal-governance release.** The project ships with a single
author and no Technical Committee. The governance structure described in
[GOVERNANCE.md](./governance.md) is the *target state* — it activates when
public maintainership opens at **v0.2.0**.

For v0.1.0:

- All decisions, including spec-level ones, are author-led.
- RFC issues are welcome and read; resolution is at author discretion until
  the TC seats are filled.
- License, project name, and CoC adoption follow the same single-author
  rule until v0.2.

This is honest. Pretending to have a Technical Committee when no one has
volunteered would be worse than admitting v0.1.0 is a one-person project.

## Volunteering

The path is open. To express interest in joining when v0.2 lands:

1. Land at least one merged PR that touches a non-trivial code path.
2. Open a "maintainer-volunteer" issue (template arrives with v0.2) describing
   which area (parser / compiler / runtime / spec / CLI / docs / corpus) you
   want to own.
3. Wait for the v0.2 public call. The author will accept up to 3 maintainers
   and form an initial TC at that point.

## Becoming a maintainer (post-v0.2)

Once v0.2 opens public maintainership, the path is:

- Land 5+ merged PRs across at least 2 packages
- Show up in reviews on others' PRs
- Demonstrate ownership in at least one area
- A current maintainer nominates you; the TC votes (simple majority)

Stepping down: open a PR removing yourself.

## Active emeritus / inactive

When a maintainer hasn't reviewed a PR or filed an issue in 6 months, they
move to the emeritus list. They can return to active simply by resuming
activity.
