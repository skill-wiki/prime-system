# Skill Wiki — 与其他方案的对比

[English](../../concept/comparison.md) · [中文](./comparison.md)

Skill Wiki 与五种向 LLM agent 提供领域知识的架构模式的对比分析。诚实定位：Skill Wiki 输的地方直说。

![全量装载 vs Skill Wiki —— 上下文窗口对比](../../assets/comparison-bulk-vs-skillwiki.png)

全量加载把整个 skill 文件灌进 agent 的 context window；Skill Wiki 让索引常驻，按需加载选中的投影。

---

## 五种模式

| 模式 | 核心思路 |
|---|---|
| **全量注入式技能** | Markdown 文件在每轮对话中以 system prompt 形式全量载入 |
| **Skill Wiki** | 类型化原子 + 边图 + 懒投影，通过索引化语料库提供知识 |
| **向量检索 RAG** | 文本 chunk 嵌入向量库，每次查询 top-k 检索 |
| **类型化知识图谱** | 本体驱动的 RDF/属性图存储，支持 SPARQL 类查询 |
| **包管理式语料库** | 版本化知识包发布到注册表，通过声明式安装使用 |

---

## 功能对比

| 功能 | 全量注入式技能 | Skill Wiki | 向量检索 RAG | 类型化知识图谱 | 包管理式语料库 |
|---|---|---|---|---|---|
| **知识类型系统** | 无 — 自由 prose | 有 — 28 种 kind，schema 强制 | 无 — chunk 是不透明文本 | 有 — 本体类 | 部分 — 仅 manifest 元数据 |
| **类型化边关系** | 无 — 最多是平表列表 | 有 — 14 种动词，一等公民 | 无 — 仅超链接 | 有 — 谓词 | 无 |
| **编译期校验** | 无 | 有 — L1 结构 + L3 图；L2 语义可选 | 无 | 部分 — schema 校验器存在，但 per-chunk 强制执行罕见 | 无 |
| **懒加载 / 渐进披露** | 无 — 全量内容永远在 | 有 — summary · core · full 三层投影 | 部分 — top-k 检索，但 chunk 是全或无 | 无 — 查询返回完整节点 | 无 — install 是全或无 |
| **Semver + 内容寻址 ID** | 无 | 有 — per-atom semver + 内容哈希 | 无 | 无 | 有 — 包级别 semver |
| **组合契约** | 无 | 有 — per-persona 的 `must-include` / `must-avoid` | 无 | 部分 — OWL 约束，实践中罕用 | 无 |
| **冲突检测** | 无 — runtime agent 困惑 | 有 — `contradicts` 和 `conflicts` 边；L3 检查 | 无 | 部分 — `owl:disjointWith`，工具依赖 | 无 |
| **跨 LLM 可移植性** | Provider 依赖 | 是 — 检索路径不含 LLM；L2 可选 | Embedding 模型依赖 | 是 | 是 |
| **离线 / 无网络检索** | 是 — 文件本地 | 是 — 编译语料库只依赖文件系统 | 需要向量数据库 | 需要图数据库 | install 后可离线 |
| **可解释的检索排名** | 无（无检索） | 是 — 每个评分轴可查 | 否 — 余弦相似度不透明 | 部分 — 查询计划可见 | 无 |
| **GPU / 向量基础设施** | 无 | 无 | 必需 | 无 | 无 |
| **写作门槛** | 低 — 写 markdown | 中 — 学习 DSL | 低 — 写 prose，切 chunk | 高 — 建模本体 | 中 — 写 manifest + 内容 |

## 逐模式点评

### 全量注入式技能

最简单的方案。写 Markdown，塞进 system prompt，零基础设施。在技能集很小（约
10 个以内）且任务类型足够单一（所有已加载知识都相关）时，这是合理的选择。

失败模式是**上下文污染**：随着技能集增长，任何一轮对话都会加载与当前任务
无关的知识。无关的 prose 不只是浪费 token —— 它会明显降低模型在真实任务上
的判断质量。我们的 benchmark 显示：把创作导向的技能集全量加载给评审导向的
任务，质量下降 13 个百分点。这不是模型 bug，是全量注入架构的必然代价。

全量注入没有任何协调原语。两个技能可以互相矛盾，没有机制能检测或通知这一
点。Agent 两边都看到，在 context 里自己解决冲突 —— 结果是不一致的。

**适合场景**：技能数不超过约 10 个，且任务类型稳定。

---

### Skill Wiki

Skill Wiki 的核心赌注是：领域知识有值得编码的结构。`fact` 不是 `rule`，不是
`pattern`。`requires` 边和 `contradicts` 边意思不同。把这种结构编码出来，
就能解锁编译期校验、图遍历、冲突检测，以及让懒加载变得可行的投影模型。

代价是**写作门槛**：贡献者需要学 DSL。回报是语料库变得可查询、可校验、可
版本化 —— 而不是只有人类能导航的 prose 堆。

投影模型（summary / core / full）是关键机制：agent 始终知道存在什么（约 3 KB
索引），但只在检索选中时才加载内容。Token 预算与任务相关性成正比，与语料库
大小无关。

**弱点见下文。**

---

### 向量检索 RAG

RAG 是知识检索的主流工业方案。它的优势是真实存在的：写 prose 即可，零写作
门槛；可扩展到百万 chunk；能跨作者未预期的领域检索；查询层不依赖特定模型。

根本局限是检索**不透明**。对 embedding 做余弦相似度，无法被查看、调偏或推
理。"这个 chunk 是一条规则，不能和另一条规则共存" —— 检索器不知道什么是
"规则"。冲突检测、组合契约、边遍历，在架构上都不存在。

RAG 的检索也与知识结构无关：共享关键词的 `fact` 和 `anti-pattern` 会得到同
等分数。Kind-aware 加权（例如设计生成任务中偏好 persona 而非 check）需要混
合架构，复杂度显著上升。

Embedding 检索还需要向量数据库、嵌入模型和 GPU 预算。

**适合场景**：语料库大（> 10 万 chunk）、以非结构化 prose 为主，不需要冲突
检测或类型化关系。

---

### 类型化知识图谱

本体驱动的存储系统（RDF、属性图、OWL）是语义最丰富的选项。类型化节点、类型
化谓词、形式化子类关系、SPARQL 或 Cypher 查询、推理引擎 —— 知识工程的完整
工具箱。

实践门槛很高。本体建模需要专业知识。查询语言对 LLM 不友好。把图查询结果
装进 LLM context 需要序列化层，大多数团队是临时拼凑的。渐进披露 —— agent
先看存在感再看内容 —— 在标准图数据库里不是一个概念。

就 AI agent 消费而言，类型化知识图谱在 schema 轴上过度工程化，在 LLM 检索轴
上工程不足。它是企业知识管理、监管本体、跨系统数据集成的正确工具。但它不是
为"约 3 KB 索引，然后懒加载原子"这种消费模式设计的。

**适合场景**：需要对大型本体做形式推理、跨系统 SPARQL 联合查询，或合规可追
溯性。

---

### 包管理式语料库

把知识包当 npm 包处理：语义版本、注册表、声明式安装、包级别的冲突解决。这
解决了全量注入完全忽视的分发和依赖管理问题。

缺口是版本和分发是**协调层**，不是**检索或校验层**。安装好的 markdown 技能
包，仍然需要某种方式加载 —— 而加载问题还没被解决。包管理器不提供类型化原
子、类型化边、投影层级，也不能对包内容做编译期校验。

Skill Wiki 的 registry 组件（`prime publish` / `prime install`）实际上就是在
类型化原子语料库上加了一层包管理。两者都有。

**适合场景**：分发、版本管理、团队间依赖管理是主要痛点，内容结构是次要需
求。

## "何时用 Skill Wiki"决策树

```
你的知识语料库有超过约 20 个单元
且有超过约 3 种任务类型？
│
├─ 否  →  全量注入式技能就够了。不要过度工程化。
│
└─ 是
    │
    检索需要可解释 / 可审计？
    │
    ├─ 否，且语料库以非结构化 prose 为主，chunk 数 > 50k
    │    →  向量检索 RAG。当冲突检测成为痛点时
    │       再考虑叠加 Skill Wiki。
    │
    └─ 是，或语料库是结构化领域知识（< 约 2 万个原子）
        │
        需要形式推理、OWL 蕴含，
        或跨系统 SPARQL 联合查询？
        │
        ├─ 是  →  类型化知识图谱。可以考虑
        │           为 LLM 消费层加 Skill Wiki 适配器。
        │
        └─ 否
            │
            跨团队的分发 / 版本管理
            是主要痛点，内容结构是次要需求？
            │
            ├─ 是  →  包管理式语料库。
            │         （一旦需要类型化原子，
            │          Skill Wiki 的 registry 也能覆盖这个需求。）
            │
            └─ 否 — 你需要类型化知识、懒加载、
                       冲突检测和组合契约
                 →  Skill Wiki。
```

## Skill Wiki 的诚实弱点

以下不是伪装成警告的未来路线图。这是截至本文撰写时（v0.1.0）的真实局限。

**1. 未经跨 LLM 大规模验证。**
所有内部 benchmark 都在单一模型上运行。检索路径（读索引 → 加载原子）在设计
上是模型无关的，但 L2 语义校验器和意图分类器尚未在其他 provider 上验证。关
于跨 LLM 可移植性的说法是架构层面的，不是实证过的。

**2. 单一语言 DSL。**
`.prime` DSL 是唯一的写作入口。贡献者必须学习它。目前没有 YAML 导入、JSON
schema 导入，也没有 prose 转原子的自动 pipeline（corpus 仓库中的
`prime-decompose` Skill 可以辅助交互式完成）。如果你的团队无法消化这个 DSL，
Skill Wiki 对你来说目前还不实用。

**3. 没有 GPU 向量检索。**
检索是纯符号化的：关键词重叠 × kind 加权 × 边遍历 × domain 匹配 × quality
分数。这很快、很可解释，但无法跨释义做语义相似性。查询中使用的术语如果不出
现在任何原子的文本里，就会漏掉相关原子。Embedding 检索在未来是可插拔的，但
v1 里没有。

**4. 单语料库成熟度。**
唯一经过生产验证的语料库是前端设计语料库（899 个原子）。`recipes` 和
`coding-style` 示例展示了协议在其他领域的用法，但没有任何大规模语料库在前端
设计以外完整走过写作 + A/B 测试 + 修复的周期。28 种 kind 和 14 种边在其他
领域的大规模使用中是否仍然顺手，尚未验证。

**5. 规模上限。**
内存中的 `_index.xml` 索引在约 10,000 个原子以内表现良好。超过这个规模，索
引本身可能撑爆 context 预算。分片（按 domain 或命名空间分成多个子索引）是预
期的缓解方案，但 v0.1.0 里尚未实现。

**6. L2 语义校验器是实验性的。**
可选的 per-atom LLM 语义校验（由 `DEEPSEEK_API_KEY` 控制）在 CI 中没有回归
测试套件。它在实践中有效；它的精度声明是说明性的，不是 benchmark 过的。

---

## 定位小结

Skill Wiki 占据一个具体的位置：**结构化领域知识 + 编译期质量保证 + 懒检索
+ 组合契约 + 团队或组织规模** —— 不是百万 chunk 的文档语料库，也不是需要推
理引擎的形式本体。

如果这个描述跟你的问题匹配，Skill Wiki 是为你设计的。
如果不匹配，上面某个其他模式可能是更合适的选择。
