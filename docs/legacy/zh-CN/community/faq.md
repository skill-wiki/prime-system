## 1. 为什么用类型化原子，而不是自由格式的 Markdown？

自由格式 Markdown 写起来简单，但程序化推理做不了。当两个 Markdown 技能文件
相互矛盾时，没有任何机制能检测出来 —— 模型两边都看到，然后在 context 里自己
解决，结果是不一致的。

类型化原子把结构显式化了。一个 `rule` 原子必须有 `claim` 字段和
`applies_when` 字段；parser 在编译时强制执行这一点。一个 `fact` 原子必须有
`statement` 和 `confidence` 分数。因为结构是声明式的，编译器就能校验它，
检索器就能按 kind 过滤，图就能遍历类型化边，投影系统就能只暴露 agent 需要的
字段 —— 而不是把所有内容都扔出去。

类型化编程语言的类比是准确的：类型不会阻止你表达想表达的内容，但
它们在运行时之前就能抓住一类错误，并让工具成为可能。

## 2. 为什么自定义 DSL，而不是 YAML 或 JSON？

三个原因，按重要性排序：

**人类写作时的可读性。** YAML 有很多坑（隐式类型转换、缩进敏感、多文档文
件）。JSON 要对每个 key 加引号。`.prime` DSL 是为人类在文本编辑器里写而设计
的：用 `"""` 的块字面量、用 `@scope/id` 语法的原子引用、读起来像英语的字段名
（`validates-with`、`must-include`）。

**词法层的原子 kind 强制。** 在 `.prime` 语法里，原子 kind 是声明的第一个
Token。这让词法器在解析函数体之前就能对未知 kind 快速报错。用 YAML/JSON
的话，kind 校验需要在解析后再做一次独立的 schema 校验，错误信息也会更差。

**向前演进空间。** 自定义语法可以独立于任何序列化格式规范来演进语法。添加新
的字段语法（比如函数签名、联合类型、范围表达式）不需要映射到 JSON Schema 或
YAML 扩展。规范自己管语法。

代价是工具引导成本：目前没有开箱即用的 `.prime` 感知编辑器插件。这是已知的
缺口。

## 3. 编译语料库需要运行 LLM 吗？

**不需要。** L1 和 L3 是完全确定性的，不需要 LLM。

- **L1**（结构性）：parser 校验字段存在性、字段类型、原子 kind schema、跨原
  子引用解析、重复 ID 检测。纯解析 —— 没有网络调用。
- **L3**（图级）：检查 `requires:` 边中的环、`must-include` 语料库存在性、
  `contradicts:` 标记。纯图算法 —— 没有网络调用。

**L2**（语义）是可选的，由 LLM 支持。它由 `DEEPSEEK_API_KEY` 环境变量控制。
当 key 不存在时，L2 被静默跳过，编译器只用 L1 + L3 继续。构建输出中会有提示：

```
[compile] L2 semantic check: SKIPPED (DEEPSEEK_API_KEY not set)
```

对大多数写作工作流来说，L1 + L3 就足够了。L2 最有价值的场景是：你想发现两
个没有共同关键词的原子之间的语义矛盾 —— 比如，两个原子各自定义了同一场景下
的正确行为，但给出了不同的建议。

## 4. 不用 MCP 可以使用 Skill Wiki 吗？

**可以。** MCP 是一种交付机制，不是必需的。

编译好的语料库是一个 JSON 文件目录。有文件系统访问权限的 agent 可以直接用
`Read` 工具读取原子。索引在 `compiled/_index.xml`。单个原子在
`compiled/<atom-id>/summary.json`、`compiled/<atom-id>/core.json`、
`compiled/<atom-id>/full.json`。

MCP server（`PRIME_DIR=... bunx @prime-lang/mcp-server-core`）是一个便利层，它把这种文件系统访问包装成结构
化查询接口（`prime_query`），并处理边遍历。在以下情况下它有用：

- 你想把语料库暴露给没有直接文件系统访问权限的 agent（比如远程或沙盒 agent）。
- 你想让查询接口处理边遍历和投影层级选择。
- 你想用 `scope: "search"` 模式做跨整个语料库的关键词检索。

如果你的 agent 能读文件，而且你愿意自己构建检索逻辑，MCP server 是可选的。

## 5. Skill Wiki 和 RAG 有什么区别？

Skill Wiki 和向量检索 RAG（检索增强生成）都在尝试解决同一个问题：在不把所有
内容都塞进 context 的前提下，给 agent 提供相关知识。

区别是架构层面的：

| 维度 | 向量检索 RAG | Skill Wiki |
|---|---|---|
| 知识结构 | 不透明的 chunk，没有类型 | 类型化原子，28 种 kind |
| 检索机制 | 对向量做余弦相似度 | 符号化：关键词 × kind × 边 × domain × quality |
| 可解释性 | 不透明 —— 只有余弦分数 | 每个评分轴都可查 |
| 冲突检测 | 无 —— 没有"冲突 chunk"概念 | `contradicts` 和 `conflicts` 边；L3 检查 |
| 组合契约 | 无 | per-persona 的 `must-include` / `must-avoid` |
| 基础设施 | 向量数据库 + 嵌入模型 | 仅文件系统 |
| 写作门槛 | 低 —— 写 prose，切 chunk | 中 —— 学习 DSL |
| 规模 | 数百万 chunk | 约 1 万个原子（不分片时） |

RAG 适合语料库大、以非结构化 prose 为主、需要跨释义语义相似性的场景。Skill
Wiki 适合知识有结构值得编码、需要可解释检索、需要编译期保证的场景。

两者不互斥：Skill Wiki 处理结构化领域知识，向量库处理非结构化参考文档 ——
这是合理的混合架构。

## 6. Skill Wiki 支持向量嵌入检索吗？

v0.1.0 不支持。检索是纯符号化的。

检索排名是以下几项的加权组合：查询和原子文本之间的关键词重叠、基于 kind 的
加权（例如设计生成任务中 `persona` 和 `template` 原子得分更高）、边遍历邻接
性、domain 匹配、quality 分数。每个维度都可查可调。

不支持向量检索意味着：查询中使用的术语如果不出现在任何原子的文本里，就会漏
掉相关原子。这是已知的局限。

可插拔的向量检索在路线图上，但不在 v1 的范围内。架构的设计使得向量分数可以
作为额外的排名轴加入，而不需要改变原子格式或投影模型。

## 7. 一个语料库的规模上限是多少？

`_index.xml` 文件 —— 它始终被加载进 agent 的 context —— 随原子数量线性增长。
对于 1,000 个原子约 3 KB，大多数 context 窗口都能轻松容纳。对于 10,000 个原
子约 30 KB，在 context 窗口较小的模型上开始有压力。

**实践建议：**

| 语料库规模 | 预期行为 |
|---|---|
| < 1,000 个原子 | 没有问题。索引约 3 KB。 |
| 1,000 – 5,000 个原子 | 监控索引大小。大多数现代模型没问题。 |
| 5,000 – 10,000 个原子 | 索引约 15–30 KB。考虑 domain 范围的子索引。 |
| > 10,000 个原子 | 需要分片。见下文。 |

**分片策略（v0.1.0 尚未实现）：** 把语料库分成多个编译子目录，每个有自己的
`_index.xml`。Agent 只加载当前任务 domain 相关的子索引。每个原子上的 `domain:`
字段和 `scope` 类型的原子专门为支持这种分片而设计。

如果你在分片实现之前碰到 1 万个原子的上限，变通方法是维护多个语料库目录，
每次会话只挂载相关的那个。

## 8. Schema 如何演进和迁移？

Schema 演进在两个层面工作：per-atom 版本化和规范版本化。

**Per-atom 版本化。** 每个原子有一个遵循 semver 的 `version` 字段。对原子内
容的破坏性变更（移除必填字段、改变字段的语义含义）会升级主版本号。原子 ID
在版本间保持稳定；版本出现在 registry manifest 里。固定到 `"~1.0.0"` 的依赖
不会自动收到主版本升级。

**内容寻址 ID。** 编译器可以选择性地在编译产物后面附上内容哈希。这意味着内
容变化的原子会产生不同的编译产物，让同一 ID 下的内容被静默覆盖变得不可能。

**规范版本化。** 协议规范（`PRIME-PROTOCOL-v1.md`）独立于实现进行版本化。规范版
本冻结在 v1.0。v2 规范在语料库层面是向后兼容的（现有原子仍然有效），除非明
确标记为破坏性变更。构建输出中编译器的 `[spec: vX]` 标签告诉你使用了哪个规
范版本。

**迁移路径。** v0.1.0 没有自动迁移工具。跨多个原子重命名字段需要脚本或批量
查找替换。这在路线图上。

## 9. Skill Wiki 支持多租户部署吗？

**支持，通过语料库隔离。** 每个租户有自己的编译语料库目录。MCP server 以
`--corpus /path/to/tenant-corpus` 启动，只服务那个语料库。租户 A 的原子对租
户 B 的 server 不可见。

**共享语料库内的命名空间隔离。** 如果更倾向于跑一个共享语料库（比如 SaaS 产
品里各租户都向共享池贡献原子），原子 ID 中的 `@scope/` 前缀提供命名空间隔
离。`prime_query` 可以按 scope 前缀过滤。`scope` 类型的原子就是专门用来在共
享语料库内声明知识领域边界的。

目前还没实现的：运行时访问控制（比如读取特定 scope 的原子需要 token）。这需
要在 MCP server 前面加中间件层，或者自定义 registry 端点。纯文件系统架构把
访问控制交给了操作系统。

## 10. 检索有多快？

对于内存中已加载的编译语料库，检索速度在**微秒到低毫秒**级别。

MCP server 在启动时加载所有编译好的 JSON 文件。`scope: "search"` 的
`prime_query` 调用会扫描内存中的原子列表并对每个原子评分。对于 1,000 个原子
的语料库，这是对约 1,000 条记录做简单算术的线性扫描 —— 通常不超过 1 毫秒。

边遍历（`scope: "related"`、`scope: "graph"`）是在预先解析好的邻接表上做图
遍历。对一个典型的有 5–10 个邻居的原子，深度 1 遍历需要数十微秒。

实践中的瓶颈不是检索，而是**原子内容加载** —— 从磁盘读取完整投影 JSON。对
于 NVMe SSD，一个 `full.json` 文件（约 400 token，约 2 KB）读取需要约
50–200 微秒。这只对检索器选中的原子做，不对整个语料库做。

如果 MCP server 是远程的，网络延迟会超过上述所有数字。

## 11. 多个 agent 可以共享一个语料库吗？

**可以。** 从 agent 的角度，编译好的语料库是只读的。多个 agent 可以同时从同
一个语料库目录读取，不需要协调。MCP server 相对于语料库内容是无状态的 ——
它在启动时加载，然后提供纯读服务，没有写入路径。

如果两个 agent 需要向同一个语料库写入（比如添加原子的写作 agent），它们应该
向各自的暂存目录写入，然后运行 `prime compile` 产生新的编译语料库。合并两个
语料库（去重、冲突解决）是编译器层面的操作；文件系统层面没有并发写入路径。

## 12. 我的领域不适合 28 种原子 kind 怎么办？

使用 `kind: custom` 并在 `custom_kind` 字段里指定你的 kind 名称。

```prime
custom MySpecialKind {
  id: "@myteam/custom-risk-assessment"
  custom_kind: "risk-assessment"
  version: "1.0.0"

  # 你需要的任何字段
  risk_level: "high"
  mitigation: "..."
}
```

用 custom kind，你会失去：
- 对 kind 专属字段的编译期 schema 校验（L1 只检查基础字段：`id`、`version`、
  `domain`）。
- Kind-aware 的检索加权（排名算法不知道 `risk-assessment` 是什么）。

你保留的：
- 边图和图遍历（14 种边动词正常工作）。
- 投影模型（summary / core / full）。
- Registry 发布 / 安装。
- L3 一致性检查（环、contradicts、缺失的 must-include 原子）。

如果某个领域专属的 kind 被证明有广泛用途，长期路径是把它作为新的一等公民
kind 提交到规范里。规范演进流程要求提供具体的使用案例、示例原子和提议的
schema。

## 13. 为什么编译器把原子内容写到磁盘，而不是保存在内存里？

因为 **agent 的 `Read` 工具是加载机制** —— 不是 IPC 调用，不是函数调用，不
是数据库查询。

当 agent 决定以完整投影加载某个特定原子时，它用路径
`compiled/@example/fact-water-boils-at-100c/full.json` 调用 `Read` 工具。这
是直接的文件系统读取。Agent 不需要跟任何进程通信；没有 IPC 开销；没有序列化
往返。原子文件就是一个文件。

这个设计决策有几个含义：

- **可审计性。** 编译好的语料库是人类可读、可用标准文件系统工具检查的。
  `cat compiled/@example/fact.../core.json` 就能用。
- **不需要守护进程。** MCP server 是可选的。有文件系统访问权限的 agent 可以
  完全跳过它。
- **可缓存性。** 操作系统层面的文件缓存自然适用。如果 10 个 agent 同时读同
  一个原子，操作系统在第一次读之后从 buffer cache 服务它。
- **内容寻址。** 文件路径由原子 ID 确定性推导出来。给定原子 ID，任何工具都
  能构造路径，不需要询问 server。

另一种方案 —— 把编译好的原子保存在内存里通过 IPC 服务 —— 会要求 MCP server
始终运行，增加延迟，并打破大多数 agent 运行时（包括 Claude Code）围绕"agent
读文件"设计的模型。

## 14. 检索排名算法是怎么工作的？

默认排名算法组合了五个维度（权重可配置，乘法叠加）：

1. **关键词重叠。** 查询 token 在原子的 `id`、`summary`、`description` 或
   tag 字段中出现了多少个。这是基线信号。

2. **Kind 加权。** 不同的原子 kind 根据推断的任务类型有不同权重。对于设计生
   成任务，`persona` 和 `template` 原子的加权高于 `check` 或 `metric` 原子。
   加权表在每个语料库里可以配置。

3. **边遍历邻接性。** 如果一个已经得分很高的原子通过 `requires` 或 `enhances`
   边指向另一个原子，那个邻居会得到二次加权。这实现了"沿图走"的启发式。

4. **Domain 匹配。** 如果查询或 context 指示了特定的 domain（比如
   `typography`、`color`、`layout`），带有该 domain 标签的原子得分更高。

5. **Quality 分数。** 每个原子可以带一个 `quality` 字段（0.0–1.0）。这由语
   料库作者设置，反映对原子正确性和完整性的置信度。作为决胜维度。

最终分数是这五个维度的加权乘积。权重在语料库 manifest 里暴露，可以通过
`prime_query` 接口在 per-query 基础上覆盖。

Topic 同义词（比如把"字体"、"typography"、"font" 映射到同一个检索 topic）在
语料库的 domain plugin 里配置。没有这些同义词，跨语言或跨术语的查询就会退化
成纯关键词重叠。

## 15. 用 Skill Wiki 生成的原子，版权归谁？

**完全由你决定。** Skill Wiki 系统（parser、compiler、runtime、CLI、MCP
server）是 Apache-2.0 的。用它来写作和分发原子，不会对原子本身施加任何版权
约束。

类比用代码编辑器写代码：编辑器的 license 不影响你用它写的代码的 license。

如果你把原子发布到公共 registry，需要在语料库 manifest 里声明 license。
Registry 会显示它。下游使用者可以按 license 过滤。

如果你引用了带有特定 license 的语料库中的原子（比如 `prime-corpus-frontend`
仓库，其中包含从 MIT license 来源派生的原子），你必须对这些原子遵守那个
license。每个语料库仓库的 `NOTICE` 文件记录了第三方归属声明。

这个仓库里的 3 个示例语料库（`hello-world`、`recipes`、`coding-style`）和系
统代码一样，都是 Apache-2.0 的。
